# Design

## Context

See `proposal.md` for motivation and scope. 当前仓库包含好礼乐专用 Skill、品牌/业务资料和项目说明页；OpenSpec 是新加入的规划与变更追踪层。框架需要服务多个品牌/产品，因此长期流程规范与单个项目事实必须分层。创意工具可变，不能让某一供应商成为流水线的前置依赖。

## Goals / Non-Goals

**Goals:**
- 建立工具无关、可跨品牌复用的项目视频生产 Skill。
- 保留产品背景采集过程，将品牌/产品事实改为项目档案输入，而非固定示例。
- 让每条视频复用同一套创作顺序、交付格式、连续性记录、质量门禁与返修规则。
- 用 OpenSpec 规格、方案和任务记录本次架构变更，实施后归档。

**Non-Goals:**
- 不为任何特定品牌、产品、平台、画风或音乐创建默认值。
- 不自动生成视频、不连接生成服务、不安装运行依赖或触发付费操作。
- 不保证流量、转化、生成模型一致性或特定工具效果。
- 不将产品背景模板当作产品事实来源；事实必须由实际项目方提供并批准。

## Decisions

1. **以一个通用项目 Skill 为入口。** 将 `haolile-video` 改为 `video-production-pipeline`，入口说明每次视频相关任务需读取项目档案模板和生产工作流。备选方案是保留品牌 Skill 再加通用 Skill；拒绝该方案，因为品牌专用入口会继续污染框架默认值。
2. **将项目背景做成空白模板和采集流程。** 模板记录项目身份、产品/服务、目标人群、场景、价值主张证据、禁区、素材授权、待确认项及审批信息。实际数据由使用者在项目开始时填入独立档案。这样保留了“先了解产品再创作”的价值，同时不把当前业务复用为事实。
3. **生产核心与任务卡分层。** Skill/流程文档定义每次都复用的创作次序、输出协议和 QA；任务卡只收集本条目标、问题、结论、音乐、时长、资产引用和交付类型。单条覆盖不能静默改写长期背景。
4. **将外部 GitHub 内容收敛为可迁移原则。** 保留来源、核验日期和许可证注意事项；去掉以好礼乐为主体的措辞、固定画风建议以及过时星数作为质量证明的表达。外部工具、规格及授权在具体任务中另行核验。
5. **不删除 OpenSpec 历史。** 本次重构前的专项资料从活跃 Skill 移除；OpenSpec proposal/spec/design/tasks 记载变更理由、契约、实现计划和归档记录。通用框架不继续附带旧品牌事实作为示例。

## Risks / Trade-offs

- [完全移除专项资料会丢失作为产品背景的实例] → 项目背景模板保留需要采集的字段；原专项内容不进入通用输出或默认档案，需时由项目方重新提供。
- [通用规范可能过于抽象] → 每条任务卡要求明确项目档案、事实来源和任务变量；不确定时提供流程性问题，不替用户填造事实。
- [多份文档可能发生规则漂移] → Skill 作为入口，工作流作为规范主文档，项目档案模板只规定输入字段，HTML 只做可视化说明；归档前验证它们一致。
- [图像/视频生成模型跨镜头仍会漂移] → 使用资产 ID、参考素材、预演、代表镜头与人工 QA，明确这只能降低风险。

## Migration Plan

1. 建立 `openspec/specs/video-production-pipeline/spec.md` 作为归档后的行为契约。
2. 创建通用 Skill 与空白项目背景/生产工作流参考文件，删除专用品牌/业务默认值。
3. 更新 HTML 为通用流水线说明，验证内容无残留品牌、特定产品或固定画风要求。
4. 运行 OpenSpec validate 和基本文件/内容检查；所有任务完成后将 change 移入 dated archive。
5. 若迁移后的通用结构不适用，优先修订模板与流程，不恢复隐式特定默认值。

## Open Questions

无。平台、风格、音乐、产品事实均作为每个具体项目可填写的配置，不影响本框架设计。
