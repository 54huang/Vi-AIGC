# Design

## Context

参见 `proposal.md` 的 Why。现有生产框架以 Markdown、表格和 Brief 文本描述信息，尚无生产记录 schema 或校验器。已有 OpenSpec 要求事实来源、素材授权、镜头连续性与质量门禁可追溯，因此结构化模型应复用这些概念，而不是另建一套生产流程。

## Goals / Non-Goals

**Goals:**

- 定义一组小型、有 schema 版本的记录，并能从单条 Brief 追溯到档案、事实、镜头、素材、审查与交付。
- 自动发现可确定性判断的数据缺失、非法状态、断链、版本不匹配、范围/有效期冲突和未满足门禁。
- 明确机器校验结果与责任人内容审查结果相互独立。
- 保持可读、可迁移、离线优先；结构化数据与人工创作说明共存。

**Non-Goals:**

- 不实现媒体数据库、资产管理平台、权限工作流或云端服务。
- 不自动判断事实真假、素材权利是否充分、法规/平台政策是否合规、创意是否有效或画面是否美观。
- 不绑定生成模型、剪辑器或发布平台；不要求已有项目一次性迁移。
- 不把自由文本创作说明改造成只能由机器生成的格式。

## Decisions

### 1. 使用 YAML 作为创作者维护的记录，JSON Schema 作为结构契约

每个项目采用文件化数据包，YAML 便于人工维护，结构契约以 JSON Schema 表达；校验器读取 YAML 后按对应 schema 验证。schema 及每条记录都显式声明版本。考虑过纯 JSON（验证工具链更直接但人工编辑较繁琐）及仅 Markdown 表格（易读但枚举、类型和关联验证较弱）；选择 YAML + JSON Schema，以后可按需导出 JSON，不要求数据库。

### 2. 使用用户确认的 ID/版本关系作为跨记录主干

逻辑模型以如下引用为核心：

```text
VideoBrief
  ├─ project_profile_id + profile_version
  ├─ claim_ids[]
  └─ shot_ids[]

Shot
  ├─ claim_ids[]
  ├─ asset_refs[]        # asset_id + version
  └─ review_refs[]

Release
  ├─ brief_id + brief_version
  ├─ shot_versions[]     # shot_id + version
  ├─ asset_refs[]        # asset_id + version
  └─ required_review_refs[]
```

`ProjectProfile` 持有或索引项目内 Claim 与 Asset 的稳定 ID/版本。引用不可仅使用可变文件名或列表行号。校验器需解析引用并指出引用方及字段路径。`Release.asset_refs` 表示所选镜头版本实际打包的素材清单；校验时与这些镜头所引用素材的闭包进行一致性检查，防止漏列或误列。`required_review_refs` 必须对应当前 Brief/镜头/素材版本的审查记录；“必需哪些审查”来自项目/生产规则，而非由单条 Release 任意缩减。

### 3. 将结构校验、语义关联校验和人工审查分开

校验分为两类机器检查：

- **结构检查**：必填字段、数据类型、枚举、格式、同包 ID 唯一性及 schema 版本。
- **关联/门禁检查**：ID 与版本是否存在、Claim/Asset 状态和声明范围是否满足任务、有效期是否覆盖计划日期、审查是否针对所选版本、Release 是否具备所有必需审查。

结果使用 `ERROR`（确定违反结构/硬门禁，阻断）、`WARN`（需要责任人确认，例如权利范围语义存疑）、`PASS`（仅表示定义的机器规则通过）。人工审查独立记录为 `pending / approved / rejected` 等，并绑定被审对象及其精确版本。机器 `PASS` 不得把人工状态改成 `approved`。

### 4. 机器检查只校验显式声明的数据，不推断隐含事实

例如，校验器可以检查 Claim 是否有来源字段、来源状态是否为已确认、适用日期是否有效；但不能确认来源是否可靠或文案是否准确。可以核对 Asset 的授权渠道字段与 Brief 渠道是否相同；若授权文本含糊或需要法律解释，应输出警告/人工复核，而非自行判断“合法”。无法可靠确定时必须 fail-closed 或警告，不得默认为通过。

### 5. 以完整样例和本地验证入口作为交付边界

提供一个小型但完整的样例包，至少覆盖项目档案、Brief、Claim、Asset、Shot、Review、Release，并能验证成功；另提供故意缺少字段、断开引用、旧版审批或过期范围的负例。提供单一本地验证入口，输出记录 ID、错误级别、字段路径、引用目标及简明修复提示。实现阶段再确定语言/依赖，避免现在把技术选型扩大成服务架构。

### 6. 渐进迁移，不破坏现有 Markdown 工作流

当前 Skill、背景模板和制作工作流继续保留面向人的说明。先新增结构化样例与并行填写指引，验证一个端到端案例，再决定是否把结构化记录设为正式任务的默认输入。旧项目没有稳定版本或授权数据时标为待补，不通过猜测补值；在迁移期可用人工审查，但不得声称其已通过机器校验。

## Risks / Trade-offs

- [重复维护 YAML 与 Markdown 会产生漂移] → 先让样例和模板引用同一组字段定义；后续只在确有维护成本时生成文档，不在首版引入复杂生成器。
- [自由文本状态导致校验边界不清] → 状态采用小型枚举；描述性判断放在 review notes 与责任人字段中，不把意见文本当机器结论。
- [JSON Schema 无法单独验证跨文件引用] → 使用一个薄的关联校验步骤；不把跨记录业务规则塞入 schema。
- [授权范围字段齐全被误认为授权充分] → 结果标签明确写“记录检查通过，不构成权利确认”；缺乏明确机器规则的情况进入人工复核。
- [版本更新令旧审批失效，增加返工] → 保留旧记录用于审计，仅将受影响对象标为需复核，不要求无关镜头重新审核。
- [一次迁移负担过高] → 先做一个真实视频的完整样例，分项目渐进采纳；不把全仓历史资料迁移列为首版前置条件。

## Migration Plan

1. 确认首版字段、枚举、schema 版本和引用规则，建立有效及无效样例。
2. 实现本地结构与关联校验入口，并用样例验证错误定位和阻断行为。
3. 选择一条新视频或低风险现有视频并行填写 Markdown 与结构化记录，记录缺失字段及实际维护成本。
4. 根据试点反馈更新 schema 和模板；由项目负责人决定何时将其纳入常规 Brief/Release 门禁。
5. 回滚时可停止调用验证器并继续原 Markdown 流程；已创建的结构化记录保留，不覆盖或删除原档案。恢复验证时用其声明的 schema 版本读取。

## Open Questions

无。首版明确采用文件化 YAML 记录、JSON Schema 结构契约、独立引用校验和人工审核状态；实现语言可在实施阶段依据仓库运行环境选择，不改变这些行为要求。
