# Repository Change Governance Specification

## Purpose

本能力约束视频生产仓库内由维护者或 Agent 发起的所有拟保留修改，使任何大小的功能、规格、Skill、测试、文档或仓库配置变更都能先有 OPSX 方案，再按任务实施、验证并留下可追溯的规格同步与归档结果。

## Requirements

### Requirement: 仓库改动必须经过 OPSX 生命周期
本仓库任何拟保留的新增、修改或删除，不论大小或文件类型，维护者与 Agent MUST 在编辑实现文件前关联一个适用的 OPSX 变更，并按 explore（需要时）、propose、update（范围变化时）、apply、验证、sync specs（有 delta spec 时）和 archive 的职责执行。只读调查与未拟保留的本地临时产物不属于仓库改动；此界线 MUST NOT 被用于绕开文档修正、测试或热修的变更记录。提案阶段 MUST NOT 顺带实施，实施必须在方案就绪后的独立 apply 步骤启动。

#### Scenario: 修正一处文档或测试
- **WHEN** 维护者计划保留一个很小的文档、测试或配置修改
- **THEN** 仍先建立或关联 OPSX 变更，记录范围、实施任务和验证结果，不以改动小为由直接编辑归档外文件

#### Scenario: 紧急修复
- **WHEN** 仓库需要尽快处理缺陷或安全问题
- **THEN** 采用精简但完整的 OPSX 变更流程，不静默跳过提案、验证或归档；确有未完成事项须如实报告而非标记完成

#### Scenario: 需求在实施中变化
- **WHEN** 已确认方案的行为、范围或验收条件发生变化
- **THEN** 先更新 OPSX 方案与任务，再实施新范围，不靠直接改代码或勾选旧任务掩盖偏差

### Requirement: 变更完成状态必须可核验
OPSX 变更 SHALL 在实施后保留任务与测试证据；有 delta spec 时 MUST 在归档前同步并核对主规格；无规格行为变化的维护变更 SHALL 明确说明跳过 delta spec 的理由，不得制造无关需求。涉及生产框架的修改 MUST 按仓库 Agent 规则检查并必要时更新 HTML 概览。未完成任务、失败验证或未同步的适用主规格不得声称变更已完成；归档与发布行为须按当时明确适用的仓库规则执行。

#### Scenario: 规格行为变更完成
- **WHEN** 一个变更含 delta spec 且实施与测试已完成
- **THEN** 主规格与 delta 内容一致，HTML 影响已评估，变更状态与归档位置可追溯

#### Scenario: 仅维护文档且不改变行为
- **WHEN** 修改不影响任何规格级行为
- **THEN** 记录无 delta spec 的原因，完成适用验证并归档，而不是为让校验通过虚构新需求

#### Scenario: 检查尚未通过
- **WHEN** 必需任务、测试、主规格同步或 HTML 一致性仍有未决项
- **THEN** 保持未完成状态并报告具体阻塞，不声称归档或发布成功
